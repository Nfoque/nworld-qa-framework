# Generation Protocol v0.1

> Status: **draft**
> Date: 2026-06-02
> Origin: internal pilot (PLAN + skill `create-e2e-spec`) + `research/insights.md`

## What it is

Protocol that defines how to generate a Playwright E2E spec from source code
and (optionally) its OpenAPI spec and Jira ticket. Designed to run as a
Claude Code skill (see `architecture/adr-001-framework-form.md`).

## Minimum inputs

| Input | Required | Source | What it provides |
|---|---|---|---|
| Component / feature path | Yes | Path to source code | testIds, interactions, routes |
| OpenAPI spec | No | Local path or URL | Endpoints, schemas, error responses |
| Jira ticket key | No | Manual or CLI | `@XRAY-{KEY}` tag for traceability |
| Existing tests | No | `e2e/` directory if present | Conventions, patterns, what is already covered |

## Pipeline

```
1. PARSE SOURCE CODE
   Read component -> extract:
   - testIds (data-testid attributes)
   - User interactions (clicks, forms, navigation)
   - API calls (endpoints the component calls)
   - Route: which URL this component maps to

2. PARSE OPENAPI (if available)
   Read spec -> extract:
   - Endpoints used by this component
   - Response schemas (what structure the backend returns)
   - Possible error states (4xx, 5xx defined in the spec)

3. PARSE JIRA (if available)
   Read ticket -> extract:
   - Acceptance criteria
   - Flows described in the story
   - XRay tag for traceability

4. ASSEMBLE CONTEXT
   Combine outputs from all 3 parsers into a structured prompt:
   - Available testIds
   - Endpoints and their response schemas
   - Acceptance criteria (if any)
   - Project conventions (if existing tests are present)

5. GENERATE SPEC
   Call the LLM with the assembled context + prompt template
   -> Output: Playwright spec in ADR-002 format
   -> See: protocol/prompt-templates/generate-e2e-spec.md

6. POST-PROCESS
   - Verify the spec compiles (correct imports, valid types)
   - Verify it uses real testIds from the component (not made up)
   - Report confidence: what percentage of the spec is evidence-based vs. inferred
```

## Output format

Playwright spec following the structure from `architecture/adr-002-playwright-setup.md`:

```typescript
import { test, expect } from "@playwright/test";

test.describe("@XRAY-{KEY} {Feature Name}", () => {
  test.beforeEach(async ({ page }) => {
    await page.goto("/{route}");
  });

  test("renders the main view", async ({ page }) => {
    await expect(page.getByTestId("{real-testid}")).toBeVisible();
  });

  // Interaction tests based on the component
  // Error tests based on the OpenAPI spec
  // Flow tests based on acceptance criteria
});
```

## Partial inputs

Not all parsers produce output. Generation adapts to what is available:

| Source Code | OpenAPI | Jira | Conventions | Result |
|---|---|---|---|---|
| ✓ | ✓ | ✓ | ✓ | Full generation — spec with render, interaction, error, and AC tests |
| ✓ | ✓ | ✗ | ✓ | No AC tests — spec covers render, interaction, and error |
| ✓ | ✗ | ✓ | ✓ | No API error tests — spec covers render, interaction, and AC |
| ✓ | ✗ | ✗ | ✓ | Basic spec — render and interactions. No error or AC |
| ✓ | ✗ | ✗ | ✗ | Minimal spec — render and interactions without respecting prior conventions |
| ✗ | — | — | — | **Error: source code is required.** Nothing is generated |

Each missing parser reduces the spec's base confidence by ~15%. A spec generated only
from source code starts at ~55% confidence (review required).

## Quality rules

Extracted from `research/insights.md`:

1. **Properties over content** — Assertions should target structural properties
   (element visible, row count, button state), not literal content
   (exact text that may change across environments/languages).

2. **Confidence + rationale** — The LLM output must include confidence per generated test.
   Tests with confidence <60% are marked with `// TODO: review — low confidence` for human review.

3. **Static analysis first** — Before calling the LLM, extract everything deterministic via parsing:
   testIds from the component, routes from the router, endpoints from the service. The LLM only
   reasons about what cannot be extracted mechanically.

4. **Real testIds, not made up** — The spec must only use `getByTestId()` with IDs that exist
   in the component. If there are no testIds, use `getByRole()` or `getByText()` and mark with
   `// TODO: add data-testid to component`.

5. **One spec per unit** — 1:1 mapping between component/feature under test and generated spec.
